# CodexGptRelay 로드맵

## 0단계: 작업 공간 준비

목표: 프로젝트의 책임 범위와 문서 위치를 고정합니다.

완료 조건:

- `F:\Antigravity\CodexGptRelay` 폴더가 존재합니다.
- README가 프로젝트 목적을 설명합니다.
- 기획서와 로드맵 문서가 저장되어 있습니다.

상태: 완료

## 1단계: Slack 왕복 검증

목표: Slack Web API로 `#codex-gpt`를 읽고 쓸 수 있는지 확인합니다.

구현 항목:

- Slack App을 생성합니다.
- Bot Token을 발급받고 `.env` 또는 로컬 설정 파일에 저장합니다.
- 필요한 Bot Token Scope를 추가합니다.
  - `channels:read`
  - `channels:history`
  - `chat:write`
- Slack `#codex-gpt` 채널 ID를 설정으로 저장합니다.
- Slack Bot을 `#codex-gpt` 채널에 초대합니다.
- 채널 최근 메시지를 읽는 스크립트를 만듭니다.
- `[to-codex]` 메시지만 감지합니다.
- `카를로스에게 전달:` 같은 사람 친화형 접두사를 감지합니다.
- 스레드 댓글은 `conversations.replies`로 확인합니다.
- 감지한 메시지의 `ts`, 작성자, 본문, 스레드 정보를 로그에 남깁니다.
- 테스트용 고정 응답을 같은 스레드에 `[codex-result]`로 답장합니다.

완료 조건:

- 사용자가 GPT에서 Slack에 요청을 남깁니다.
- Codex relay가 요청을 감지합니다.
- Slack 스레드에 테스트 결과가 남습니다.
- 같은 메시지가 두 번 처리되지 않습니다.

주요 위험:

- Slack API 제한에 걸릴 수 있습니다.
- 같은 계정 표시명 때문에 발신자를 구분하기 어려울 수 있습니다.

대응:

- 처음에는 10초 간격의 폴링을 사용합니다.
- `HTTP 429`가 오면 `Retry-After` 값만큼 기다립니다.
- 발신자보다 접두사와 `task_id`를 기준으로 처리합니다.

## 2단계: 파일 큐 연결

목표: Slack 메시지를 Codex app이 읽을 수 있는 로컬 작업 파일로 변환합니다.

구현 항목:

- `inbox`, `outbox`, `state`, `logs` 디렉터리를 만듭니다.
- `[to-codex]` 메시지를 `inbox/task_<task_id>.md`로 저장합니다.
- `logs/relay_events.jsonl`에 `task_created` 이벤트를 남깁니다.
- 처리한 Slack 메시지 `ts`를 `state/processed_messages.json`에 저장합니다.
- `outbox/*.md`를 감지해 Slack 스레드에 전송하는 흐름을 만듭니다.

완료 조건:

- `[to-codex]` 메시지가 들어오면 `inbox` 작업 파일이 생깁니다.
- 사람이 `outbox`에 결과 파일을 만들면 데몬이 Slack 스레드에 답장합니다.
- 같은 `outbox` 결과 파일이 두 번 전송되지 않습니다.

주요 위험:

- 상태 파일이 깨지면 메시지가 중복 처리될 수 있습니다.
- `outbox` 파일이 아직 작성 중일 때 데몬이 읽을 수 있습니다.

대응:

- 상태 파일 저장 전 임시 파일에 먼저 쓰고 교체합니다.
- `outbox` 파일은 `.pending.md`로 작성한 뒤 완료 시 `.md`로 이름을 바꾸는 규칙을 둡니다.
- 결과 파일에는 `task_id`, `status`, `thread_ts`, `message`를 필수로 둡니다.

## 3단계: Codex app 감시 운영

목표: Codex app이 데몬 로그와 `inbox`를 라이브 서버 로그처럼 보고 작업하는 운영 방식을 고정합니다.

구현 항목:

- `inbox` 작업 파일 형식을 문서화합니다.
- `outbox` 결과 파일 형식을 문서화합니다.
- Codex app이 새 작업을 확인할 때 사용할 체크리스트를 만듭니다.
- 작업 완료 시 `outbox`에 남길 결과 템플릿을 만듭니다.
- 위험한 작업은 `[codex-question]` 결과로 돌려보내는 규칙을 문서화합니다.

완료 조건:

- Codex app에서 `logs/relay_events.jsonl`과 `inbox`만 보고 새 작업을 파악할 수 있습니다.
- Codex app이 결과 파일을 만들면 데몬이 Slack에 전송합니다.
- 사용자는 Codex 화면을 보지 않아도 GPT를 통해 결과를 받을 수 있습니다.

주요 위험:

- Codex app이 항상 자동으로 깨어 있는 것은 아닙니다.
- 작업 처리 속도는 사람이 Codex app을 어떻게 운영하느냐에 따라 달라질 수 있습니다.

대응:

- 1차는 반자동 운영으로 둡니다.
- 나중에 별도 자동화가 필요하면 하트비트 또는 app-server 호출을 보조 선택지로 검토합니다.

## 4단계: 작업 상태와 로그 정리

목표: 데몬이 장시간 켜져 있어도 작업 상태를 추적할 수 있게 만듭니다.

구현 항목:

- `state/processed_messages.json` 저장
- `state/posted_results.json` 저장
- `state/tasks.json` 저장
- `logs/relay_events.jsonl` 저장
- 작업 상태 전이 기록
- 데몬 재시작 시 상태 복구

완료 조건:

- 데몬 재시작 후에도 이미 처리한 메시지를 다시 처리하지 않습니다.
- 작업 실패 이유를 로그에서 확인할 수 있습니다.
- 최근 작업 상태를 명령으로 확인할 수 있습니다.

주요 위험:

- 상태 파일이 깨지면 중복 처리될 수 있습니다.

대응:

- 상태 파일 저장 전 임시 파일에 먼저 쓰고 교체합니다.
- JSON 파싱 실패 시 백업 파일을 만들고 새 상태로 시작합니다.

## 5단계: 사용자 확인 흐름

목표: 위험한 작업을 자동 실행하지 않고 GPT를 통해 사용자에게 확인받습니다.

상태: 완료

구현 항목:

- `outbox` 결과 파일에 `needs_user` 필드를 둡니다.
- 확인이 필요한 경우 `[codex-question]` 답장을 Slack에 남깁니다.
- GPT가 사용자의 답을 `[to-codex-reply]` 형식으로 Slack에 남기면 기존 작업에 연결합니다.
- 작업 상태를 `waiting_for_user`에서 `running`으로 되돌립니다.
- `task_id`가 없는 스레드 댓글은 `thread_ts`로 기존 작업을 찾습니다.

완료 조건:

- Codex가 질문을 남깁니다.
- 사용자가 GPT에서 답합니다.
- GPT가 Slack에 답을 전달합니다.
- Codex가 같은 작업을 이어서 처리합니다.

주요 위험:

- 답변이 원래 작업과 잘못 연결될 수 있습니다.

대응:

- 질문과 답변에는 `task_id`를 권장합니다. 없으면 같은 Slack 스레드의 기존 작업으로 연결합니다.
- `thread_ts`가 다른 답변은 무시합니다.

## 6단계: Notion 문서 작업

목표: 문서 작업과 결정 기록을 Codex app의 Notion 커넥터로 처리합니다.

상태: 부분 완료

구현 항목:

- Notion 저장 대상 데이터베이스 또는 페이지 구조를 정의합니다.
- 문서 작업은 Notion에서 처리하고, 코드 작업은 Git에서 처리한다는 운영 원칙을 문서화합니다.
- 완료된 작업의 요약, 결정 사항, 할 일, 열린 질문을 Notion에 저장합니다.
- Slack 메시지 링크와 Git 커밋 또는 작업 로그 경로를 함께 저장합니다.

완료 조건:

- Codex app이 Notion 커넥터로 문서를 생성하고 수정할 수 있습니다.
- 사용자는 Notion에서 기획서와 작업 결정을 찾을 수 있습니다.
- 데몬은 Notion API를 직접 호출하지 않습니다.

주요 위험:

- Notion 구조가 자주 바뀌면 문서 위치를 찾기 어려울 수 있습니다.

대응:

- 처음에는 자유 문서 페이지와 단순 데이터베이스로 저장합니다.
- 나중에 작업 로그용 데이터베이스 속성을 고정합니다.

## 7단계: 제한된 자동 실행

목표: 필요할 때만 Codex app-server 또는 Codex CLI를 보조 실행자로 붙입니다.

구현 항목:

- 허용 작업 목록을 설정 파일에 둡니다.
- 답변 생성, 문서 초안, 요약 같은 낮은 위험 작업부터 자동 처리합니다.
- 파일 수정, 삭제, 대량 이동, Git push는 기본 금지합니다.
- 위험한 작업은 `[codex-question]`으로 사용자 확인을 요청합니다.
- app-server를 쓸 경우 기본 권한은 `read-only` 또는 제한된 `workspace-write`로 둡니다.

완료 조건:

- 낮은 위험 작업은 Slack 요청만으로 처리됩니다.
- 위험한 작업은 확인 없이는 실행되지 않습니다.
- 실행 결과와 변경 파일이 Slack 답장에 남습니다.

주요 위험:

- 자동 실행 범위가 커지면 실수의 피해가 커집니다.

대응:

- 허용 목록 방식으로만 확장합니다.
- 작업별 로그와 결과 요약을 필수로 남깁니다.

## 8단계: Socket Mode 전환 검토

목표: Slack 폴링 호출을 줄이고 더 빠르게 메시지 이벤트를 받는 방식을 검토합니다.

구현 항목:

- Slack Socket Mode 설정 가능 여부를 확인합니다.
- 현재 폴링 방식과 Socket Mode의 설정 비용을 비교합니다.
- 이벤트 중복 수신, 재연결, 장애 대응 방식을 설계합니다.

완료 조건:

- 10초 폴링으로 충분한지 판단합니다.
- 더 빠른 반응이 필요할 때 Socket Mode로 전환할 수 있는 기준을 정합니다.

주요 위험:

- Socket Mode 설정은 폴링보다 복잡합니다.

대응:

- 1차와 2차 구현에서는 폴링을 유지합니다.
- API 제한이나 반응 속도가 문제가 될 때만 전환합니다.

## 9단계: 장기 운영

목표: 매일 사용할 수 있는 안정적인 개인 작업 중계기로 만듭니다.

구현 항목:

- Windows 시작 시 데몬 실행 선택지
- 상태 확인 명령
- 최근 오류 확인 명령
- Slack API 제한 대응
- 데몬 중복 실행 방지
- 구성 파일 문서화
- Slack Bot Token 보관 규칙 문서화

완료 조건:

- 사용자는 GPT 화면에서 요청하고 결과를 받을 수 있습니다.
- Codex 화면을 직접 보지 않아도 대부분의 작업 상태를 알 수 있습니다.
- 문제가 생기면 Slack과 로그에서 원인을 확인할 수 있습니다.

주요 위험:

- 데몬이 조용히 멈추면 사용자가 원인을 모를 수 있습니다.

대응:

- 시작, 종료, 오류를 Slack에 `[codex-status]`로 남깁니다.
- 일정 시간 동안 응답이 없으면 상태 확인 메시지를 남기는 방식을 검토합니다.
